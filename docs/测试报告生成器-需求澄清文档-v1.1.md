## 三、需求缺口与歧义分析

### 缺口 #1：FR1.1 多框架共存时的检测优先级不明确

**描述**：项目可能同时存在 `jest.config.ts` 和 `vitest.config.ts`，检测优先级未定义。

**建议方案**：
1. 用户显式指定 > 配置文件推断；
2. 配置文件推断时，按 `vitest.config.*` > `jest.config.*` 优先级（Vitest 兼容 Jest API，选更现代的框架）；
3. 若同时存在且无法自动判定，输出诊断信息并提示用户通过 `test_command` 指定。

> **CR 修复说明 (Major M2)**：补充"结果收集阶段"的优先级规则——当测试执行后同时产出多种格式的结果文件时：
> - 框架原生 JSON（如 Jest JSON reporter 输出） > JUnit XML（同目录）；
> - 与边界条件 E8 保持一致的优先级语义，避免配置文件推断阶段与结果收集阶段的优先级冲突。

**优先级**：P0（M1 阶段必须处理）

---

### 缺口 #2 + #9（合并）：测试执行失败的诊断信息与超时策略

> **CR 修复说明 (Blocker #1)**：原缺口 #2（诊断信息粒度）与缺口 #9（超时策略）存在语义重叠——两者均涉及 `timeout` 场景，但未说明超时发生的诊断信息应如何组合。现合并为统一的「测试执行失败诊断与超时策略」缺口。

**描述**：
- FR1.4 要求"给出明确诊断信息"，但未说明诊断信息应包含哪些字段；
- 测试执行超时策略未定义（R2 已指出耗时不可控）；
- 超时场景下的诊断信息应同时满足诊断信息粒度要求与超时策略标注。

**建议方案**：

**A. 诊断信息结构**（所有执行失败场景通用）：
诊断信息至少包含：
- 退出码 (exit code)
- 标准错误输出前 500 字符（截断）
- 失败原因分类：`command_not_found` / `config_error` / `runtime_error` / `timeout`
- 建议操作（如"请检查 {framework} 是否已安装"）

**B. 超时策略**（`timeout` 分类专用）：
- 默认超时：300 秒（5 分钟）；
- 可通过 `test_timeout` 配置项覆盖；
- 超时后：终止测试进程，报告生成不中断，摘要中标注"测试执行超时（部分结果可能不完整）"；
- 依赖 Agent 运行时的后台任务能力（与 R2 一致）。

**C. 超时场景的诊断信息组合**：
- 当 `failure_reason = timeout` 时，诊断信息同时包含 A 中的四个字段 + B 中的超时标注文案；
- `test_timeout` 配置项直接联动 `timeout` 分类码，超时诊断信息中注明实际配置的超时值；
- 报告摘要中额外标注"测试执行超时（{N} 秒），部分结果可能不完整"。

**优先级**：P0

### 缺口 #3：FR2 覆盖率章节的阈值文件清单规则未定义

**描述**："低于阈值的文件清单"中阈值来自哪里？如何定义？

**建议方案**：
- 通过 `coverage_min_pct` 配置项设置（默认值：语句 80%、分支 70%、函数 80%、行 80%）；
- 低于任一阈值的文件列入清单；
- 若 `coverage=off` 或覆盖率数据不可获取，该章节标注"未获取 (coverage 未启用)"。

> **CR 修复说明 (Minor m1)**：原命名为 `coverage_threshold`，与缺口 #5 的 `fail_threshold`（通过率阈值）命名相似易混淆。已重命名为 `coverage_min_pct`，明确语义为覆盖率最低百分比阈值。

**优先级**：P1（覆盖率章节整体在 M2）

### 缺口 #4：FR3.2 输出目录不存在时的行为未定义

**描述**：`output_path` 默认 `reports/`，若该目录不存在应如何处理？

**建议方案**：

- 创建失败时返回明确错误（如权限不足），而非静默降级。

**优先级**：P0

### 缺口 #5：FR4.2 fail_threshold 的语义与默认行为不明确

**描述**：`fail_threshold` 默认值为"无"，但以下问题未澄清：
- 阈值单位是百分比（如 80 表示 80%）还是绝对数值？
- 当通过率低于阈值时，报告"结论标记为不达标"的具体表现形式是什么？
- 阈值与"通过率"的比较是 `>=` 还是 `>`？

**建议方案**：
- 阈值单位：百分比整数（0-100），默认值 `-1`（即不启用）；
- 比较规则：通过率 <= fail_threshold 时触发不达标（当 fail_threshold=0 时，0% 通过率也会触发）；
- 触发时：摘要章节整体结论改为 `⚠️ 不达标 (通过率 {x}% <= 阈值 {y}%)`，保留 ✅/❌ 标识用例级别结论；
- 不达标≠报告生成失败，报告仍正常产出。

> **CR 修复说明 (Major M3)**：原建议默认值 `0` 存在语义歧义——若通过率 = 0%，`0 < 0` 为 false，不触发不达标。已修正为默认值 `-1`（表示不启用），并将比较规则改为 `<=`，确保 0% 通过率时也会触发。

**优先级**：P1（M2 阶段）

### 缺口 #6：NFR3 凭据过滤策略未定义

**描述**："错误堆栈须过滤敏感路径外的凭据内容"——但"凭据"的定义和过滤策略不明确。

**建议方案**：
- **过滤目标**：环境变量值中匹配已知密钥模式的内容（如 `AWS_SECRET_*`、`API_KEY`、`TOKEN`、`PASSWORD`、`PRIVATE_KEY`）；
- **过滤策略**：仅当匹配串出现在 `KEY=VALUE` 模式中或紧跟 `secret`/`token`/`key`/`password`/`credential` 等标识符时，才对其中的 base64/hex 长串（`[A-Za-z0-9+/=]{20,}`）替换为 `***REDACTED***`；
- **白名单路径**：保留源文件路径、测试用例名、框架内置字段；
- **实现位置**：在报告渲染阶段统一过滤，而非解析阶段逐个处理。

> **CR 修复说明 (Minor m2)**：原过滤正则 `[A-Za-z0-9+/=]{20,}` 过于宽泛，可能误伤非凭据内容（如 base64 编码的测试数据、截图）。已增加上下文约束：仅当匹配串出现在 `KEY=VALUE` 模式中或紧跟凭据相关标识符时才过滤。

**优先级**：P0（安全相关）

---

### 缺口 #7：FR2 用例明细超过 200 条时的截断策略未定义

**描述**：原文"超过 200 条时截断并注明"，但截断方式未说明。

**建议方案**：
- 截断方式：保留前 200 条（按文件分组后按文件名排序，组内按用例名排序），其余丢弃；
- 注明格式：`> ⚠️ 用例总数 {N} 条，已截断展示前 200 条，完整明细请查看原始结果文件。`
- 附录中保留原始结果文件的 **绝对路径**，供用户自行查阅完整数据。

> **CR 修复说明 (Major M1)**：原方案"附录中保留原始结果文件路径"未区分执行模式与解析模式——解析模式下 `result_file` 可能为相对路径，后续读者无法定位。已明确要求附录中使用绝对路径，无论何种模式均保证路径可追溯。

**优先级**：P0

---

### 缺口 #8：AC1 中"摘要数据与框架原始输出一致"的验证标准不明确

**描述**：什么算"一致"？数值精确匹配 vs 允许舍入误差？

**建议方案**：
- 用例总数、通过/失败数：精确匹配（整数比较）；
- 跳过数：按框架语义归一化后精确匹配（见下方映射表）；
- 通过率：保留 2 位小数，与框架输出四舍五入后一致；
- 总耗时：精确到毫秒，与框架输出一致。

**跨框架跳过数归一化映射表**：

| 框架 | 原始字段 | 归一化规则 |
|------|----------|------------|
| Jest | `pending` + `skipped` | 两者求和计入跳过总数 |
| Vitest | `skipped` | 直接计入跳过总数 |
| pytest | `skipped`（含 `skip` + `xfail`） | 直接计入跳过总数 |
| JUnit XML | `<skipped>` 属性 | 直接计入跳过总数 |

> **CR 修复说明 (Major M4)**：不同框架对"跳过"的定义不同（Jest 含 `pending`，Vitest 仅 `skipped`，pytest 含 `xfail`），若不做语义归一化，精确匹配的要求可能导致假阳性验证失败。已补充跨框架跳过数归一化映射表，确保各框架结果字段到报告模型的映射一致。

**优先级**：P0

### 缺口 #10：同一秒内多次生成报告的文件名冲突

**描述**：默认文件名模板 `test-report-<YYYYMMDD-HHmmss>.md`，同一秒内多次调用会覆盖。

**建议方案**：
- 文件名增加毫秒精度：`test-report-<YYYYMMDD-HHmmss-SSS>.md`；
- 若仍冲突（极端情况），追加 `-{n}` 后缀（n 从 1 递增）。

**优先级**：P1

### 缺口 #11：FR2 覆盖率章节中"低于阈值"的基准阈值与 NFR5 插件式架构的交互

**描述**：不同覆盖率工具（Istanbul、c8、coverage.py）输出的覆盖率维度不同，NFR5 插件式结构如何统一处理？

**建议方案**：
- 定义覆盖率标准化中间表示 (IR)：

```json
{
  "lines":       { "covered": 1200, "total": 1500, "pct": 80.0 },
  "statements":  { "covered": 1100, "total": 1400, "pct": 78.57 },
  "branches":    { "covered": 300,  "total": 500,  "pct": 60.0 },
  "functions":   { "covered": 80,   "total": 100,  "pct": 80.0 },
  "files": [
    { "path": "src/utils.ts", "lines": { "covered": 50, "total": 100, "pct": 50.0 }, "branches": { "covered": 5, "total": 20, "pct": 25.0 } },
    { "path": "src/auth.ts",  "lines": { "covered": 200, "total": 200, "pct": 100.0 }, "branches": null }
  ]
}
```

**IR 职责边界**：
- **IR 是解析器（Parser）的输出，由报告渲染器（Renderer）消费**；
- 解析器接口契约：`parse(coverageSourcePath) → CoverageIR`；
- 每个维度字段（`lines`、`statements`、`branches`、`functions`）为 **可选**（缺省 = `null`），渲染器对 `null` 字段标注"未获取"；
- 解析器不强制要求产出完整 IR，覆盖率工具仅输出部分维度时，缺失维度即为 `null`；
- `files` 维度为文件级覆盖率列表，支持"低于阈值的文件清单"渲染；
- 每个框架解析器负责将原生格式映射到 IR，覆盖率章节渲染器只消费 IR，不感知原始格式。

> **CR 修复说明 (Blocker #2)**：原 IR 定义未明确解析器与渲染器的职责边界、缺失字段的处理方式、以及文件级覆盖率支持。现已明确：IR 为解析器输出/渲染器输入；各维度字段可选且 `null` 时标注"未获取"；补充 `files` 维度支持文件级覆盖率清单。

**优先级**：P1（M2）

## 四、边界条件与异常场景补充

| 编号 | 场景 | 预期行为 | 优先级 |
|------|------|----------|--------|
| E1 | 测试全部跳过（0 通过，0 失败，N 跳过） | 通过率显示 N/A，结论标注"无有效用例执行" | P0 |
| E2 | 测试用例数为 0 | 报告正常生成，摘要显示 0 用例，结论标注"未发现测试用例" | P0 |
| E3 | 解析模式下结果文件不存在 | 返回明确错误：`结果文件不存在: {path}`，不生成空报告 | P0 |
| E4 | 解析模式下结果文件格式无法识别 | 返回明确错误：`无法识别结果文件格式: {path}，支持的格式: Jest JSON, Vitest JSON, JUnit XML` | P0 |
| E5 | 覆盖率文件存在但内容为空 | 覆盖率章节标注"未获取 (覆盖率数据为空)" | P1 |
| E6 | 用户指定了不存在的 test_command | 同 FR1.4，返回诊断信息：`command_not_found` | P0 |
| E7 | 测试执行产生大量输出 (>10MB) | 截断存储，保留前 1MB，附录注明"原始输出已截断" | P1 |
| E8 | 多个测试框架同时产生结果（如 Jest + JUnit） | 优先使用框架原生格式（JSON），JUnit XML 作为兜底不冲突；与缺口 #1 结果收集阶段优先级一致 | P0 |

> **CR 修复说明 (NFR1 备注, Minor m3)**：E7 中 1MB 文本的渲染和凭据过滤（缺口 #6）可能超过 NFR1 的 5 秒限制。已在 NFR1 中增加备注：**5 秒性能指标不含大文件凭据过滤与截断处理**，渲染阶段可设定独立超时（如 30 秒）。

## 七、安全规范补充（CR 安全检查新增）

以下安全规范基于 CR 报告安全检查（第五节）的 5 项检查结果补充，原 NFR3 已覆盖凭据过滤与环境变量泄露，新增以下 3 项：

### 7.1 报告文件权限
- 生成的报告文件默认权限为 `0644`（owner 可读写，group/other 只读）；
- 在多用户环境中防止报告内容被非授权用户修改或删除。

### 7.2 Markdown 特殊字符转义
- 测试用例名、错误信息中包含的 Markdown 特殊字符（`|`、`#`、`<`、`>`、`*`、`_`、`` ` ``）须转义；
- 防止用例名中的特殊字符破坏报告表格结构或产生非预期的格式渲染。

### 7.3 用户主目录路径脱敏
- 堆栈中的用户主目录路径（如 `/home/username/`、`/Users/username/`、`C:\Users\username\`）替换为 `$HOME`；
- 与 NFR3 凭据过滤配合，构成完整的敏感信息脱敏策略。

### 7.4 堆栈路径过滤
- 除凭据内容外，增加对用户主目录路径的过滤，脱敏后保留项目相对路径和框架内置路径。

## 八、架构关注点补充（CR 架构评估新增）

基于 CR 报告架构评估（第六节）的 3 项关注点，补充以下设计指导：

### 8.1 解析器注册机制
- 采用 **显式优先级常量** 而非依赖注册顺序来控制多框架检测优先级；
- 每个解析器声明 `priority: number`，检测时按优先级降序排列，避免注册顺序变更导致行为不一致。

### 8.2 报告渲染器插件化
- 与解析器对称，采用插件式渲染器架构，统一 `IRenderer` 接口；
- 接口契约：`render(reportData: ReportIR) → string`；
- Markdown / HTML / JSON 三种输出格式各自实现 `IRenderer`，通过配置项 `output_format` 选择。

### 8.3 统一配置模型
- 定义 `ReportConfig` 接口，集中管理所有配置项及默认值；
- 配置项来源优先级：用户显式指定 > 环境变量 > 配置文件 > 默认值；
- 当前涉及配置项：`test_command`、`result_file`、`output_format`、`output_path`、`coverage`、`fail_threshold`、`test_timeout`、`coverage_min_pct`、`output_language`。
