## 二、需求逐项澄清分析

### 2.1 需求1：部门树形结构

#### ✅ 已明确
| 项 | 决策 |
|---|---|
| 数据模型 | `parent_id` 自引用，树形组装 |
| 加载策略 | 懒加载，按需请求子节点 |
| 拖拽 | `PUT /api/departments/{id}/move`，传 `newParentId` |
| 默认展开 | 第一级默认展开 |

#### ⚠️ 待澄清 & 自主决策

| # | 歧义/缺失点 | 风险等级 | 自主决策 | 决策依据 |
|---|---|---|---|---|
| 1 | 树层级深度限制？ | 中 | **限制最大 6 层**，超出返回业务错误 | 避免无限嵌套导致性能问题；6 层覆盖绝大多数企业（公司→BG→部门→中心→组→小组） |
| 2 | 拖拽循环引用校验？ | 高 | **后端必须校验**：禁止将父节点移到自身或子孙节点下 | 否则树结构被破坏，业务不可用 |
| 3 | 部门排序？ | 中 | 增加 `sort_order` 字段（int），支持手动排序 | 默认按创建时间排序不满足业务需要 |
| 4 | 部门删除？ | 高 | **支持逻辑删除**：有人员或子部门的部门不可删除，返回明确错误提示 | 防止数据孤岛 |
| 5 | 部门属性字段？ | 中 | 最小字段集：`name`、`parent_id`、`sort_order`、`manager_id`、`status`、`created_at`、`updated_at` | 满足基本业务，后续可扩展 |
| 6 | 权限过滤？ | 高 | 树接口**不做权限过滤**，返回完整树；权限在前端 + 人员列表接口控制 | 简化后端，避免前端树不完整 |
| 7 | 部门编码？ | 低 | 暂不引入，后续按需扩展 | 减少初期复杂度 |

#### ⚠️ 待澄清 & 自主决策

| # | 歧义/缺失点 | 风险等级 | 自主决策 | 决策依据 |
|---|---|---|---|---|
| 1 | 工号格式规则？ | 中 | 允许字母数字组合，长度 4-32，前端 + 后端双重校验 | 兼容不同企业编码规范 |
| 2 | 工号是否自动生成？ | 中 | **支持两种模式**：手动输入（默认）或自动生成（配置开关）；自动生成规则：`EMP{yyyyMMdd}{4位序号}` | 兼顾灵活性和自动化 |
| 3 | 手机号校验规则？ | 中 | 中国大陆手机号：`1[3-9]\d{9}`；预留国际区号扩展字段 | 当前需求明确为国内场景 |
| 4 | 额外员工字段？ | 高 | 最小字段集：`name`、`employee_no`、`phone`、`dept_id`、`position`、`email`、`hire_date`、`status`、`created_at`、`updated_at` | 邮箱和入职日期是基础 HR 属性 |

| 6 | 唯一性范围？ | 高 | **全局唯一**（跨所有状态），离职员工的工号/手机号不可复用 | 防止历史数据关联混乱 |
| 7 | 同部门同名？ | 低 | 不做限制，仅提示但不阻止 | 现实中存在同名情况 |

### 2.3 需求3：人员调动（级联更新与快照）

#### ✅ 已明确
| 项 | 决策 |
|---|---|
| 核心逻辑 | 更新 `dept_id` |
| 审批流级联 | 触发审批流节点变更（如审批人从原主管变为新主管） |
| 审计记录 | 写入调动记录表 |
| 前端确认 | 弹出警告提示 |

#### ⚠️ 待澄清 & 自主决策

| # | 歧义/缺失点 | 风险等级 | 自主决策 | 决策依据 |
|---|---|---|---|---|
| 1 | 进行中的审批流怎么处理？ | **高** | **保留原审批链**：已发起的审批按原路径继续，调动后新发起审批按新路径 | 避免审批中途变更审批人导致混乱 |
| 2 | 审批流节点变更的范围？ | 高 | 仅更新**默认审批流模板**中的节点人员，不修改已实例化的审批流 | 模板与实例分离，保证数据一致性 |
| 3 | 调动记录表字段？ | 中 | `id`、`employee_id`、`from_dept_id`、`to_dept_id`、`from_position`、`to_position`、`reason`、`operator_id`、`created_at` | 覆盖完整审计链 |
| 4 | 是否支持批量调动？ | 中 | **不支持**（v1），仅单条调动 | 减少初期复杂度，批量场景后续按需加 |
| 5 | 调动生效时间？ | 低 | **立即生效**（以操作时间为准），不设未来生效日期 | 简化逻辑 |
| 6 | 调回原部门？ | 低 | 允许，正常记录调动历史 | 无业务限制理由 |
| 7 | 调动审批流？ | 中 | **暂不引入调动审批**，直接生效；后续可扩展为审批流驱动 | v1 简化，HR 操作视为已审批 |

### 2.4 需求4：员工离职（逻辑删除与状态隔离）

#### ✅ 已明确

#### ⚠️ 待澄清 & 自主决策

| # | 歧义/缺失点 | 风险等级 | 自主决策 | 决策依据 |
|---|---|---|---|---|
| 1 | 离职后可否复职？ | 高 | **支持复职**：`PUT /api/employees/{id}/reinstate`，恢复为在职状态，重新分配部门 | 现实中常见，需记录复职历史 |
| 2 | 离职日期可否早于今天？ | 中 | **允许补录**（不超过当前日期 30 天前），需记录操作时间与离职日期两个字段 | 人事操作常有滞后性 |

| 4 | 数据保留期限？ | 低 | 逻辑删除后**永久保留**，不做物理删除 | 合规要求，法律追溯期 |

| 6 | 批量离职？ | 中 | **不支持**（v1），仅单条操作 | 与批量调动同理 |
| 7 | 离职后部门人员统计？ | 低 | 离职员工不计入部门人数统计 | 统计口径为在职人员 |

## 三、跨需求澄清

### 3.1 权限模型

| # | 决策 | 依据 |
|---|---|---|
| 角色定义 | 超管（admin）、HR（hr）、部门主管（dept_manager）三种角色 | 覆盖需求文档中的两类角色 + 系统管理 |
| 权限粒度 | 接口级 RBAC + 数据级行权限（部门主管只看本部门及子部门） | 部门主管的数据范围由 `dept_id` 树决定 |
| 超管与 HR 区别 | 超管可管理系统配置；HR 可管理所有人员与部门；v1 阶段两者权限等同 | 简化初期实现 |

### 3.2 数据模型（核心表）

```sql
-- 部门表
-- path 字段为物化路径（如 "1-2-5"），用于加速子孙节点查询，避免递归 CTE
departments (id, name, parent_id, path, sort_order, manager_id, status, created_at, updated_at)

-- 员工表
-- dept_id 必须建立索引，用于按部门检索人员列表
employees (id, name, employee_no, phone, email, dept_id, position, hire_date, 
           status, login_enabled, created_at, updated_at)
CREATE INDEX idx_employees_dept_id ON employees(dept_id);

-- 调动记录表
transfer_records (id, employee_id, from_dept_id, to_dept_id, from_position, 
                  to_position, reason, operator_id, created_at)

-- 操作日志表
audit_logs (id, operator_id, action, target_type, target_id, detail, created_at)
```

### 3.3 接口设计补齐

| 接口 | 方法 | 说明 |
|---|---|---|

| `GET /api/departments/{id}/children` | GET | 懒加载：获取指定节点的直接子部门 |
| `POST /api/departments` | POST | 新增部门 |
| `PUT /api/departments/{id}` | PUT | 编辑部门 |
| `DELETE /api/departments/{id}` | DELETE | 逻辑删除部门（需校验无人员/子部门） |
| `PUT /api/departments/{id}/move` | PUT | 拖拽移动部门 |
| `GET /api/employees` | GET | 人员列表（分页 + 筛选 + 搜索） |
| `GET /api/employees/{id}` | GET | 人员详情 |
| `POST /api/employees` | POST | 新增员工 |
| `PUT /api/employees/{id}` | PUT | 编辑员工 |
| `GET /api/employees/check` | GET | 唯一性校验 |
| `POST /api/employees/{id}/transfer` | POST | 人员调动 |
| `PUT /api/employees/{id}/resign` | PUT | 办理离职 |
| `PUT /api/employees/{id}/reinstate` | PUT | 复职 |
| `GET /api/employees/{id}/transfer-history` | GET | 调动历史 |

### 3.4 分页与搜索

| 项 | 决策 |
|---|---|
| 分页 | 标准分页：`page`（从1开始）、`pageSize`（默认20，最大100） |
| 搜索 | 支持按姓名、工号、手机号模糊搜索；参数 `?keyword=xxx` |
| 筛选 | 支持按状态（`status`）、部门（`deptId`）筛选 |

### 3.5 并发与数据一致性

| 场景 | 处理策略 |
|---|---|
| 同一员工同时被调动和离职 | 乐观锁（`version` 字段），后者操作失败返回冲突错误 |
| 部门被删除时仍有员工 | 外键约束 + 业务校验，拒绝删除 |
| 工号/手机号并发重复 | 数据库唯一索引兜底，捕获 `DuplicateKeyException` 返回友好提示 |

### 3.6 数据库设计要点

| 要点 | 说明 |
|---|---|
| 部门表 `path` 字段 | 物化路径（如 `1-2-5`），维护时在插入/拖拽时更新，用于加速子孙节点查询，避免递归 CTE 性能问题 |
| 员工表 `dept_id` 索引 | 必须建索引，按部门检索人员列表是高频操作 |
| 逻辑删除 | 统一使用 `status` 字段区分在职/离职，不使用 `is_deleted`；查询默认 `WHERE status = 'active'` |

### 3.7 前端状态管理

| 要点 | 说明 |
|---|---|
| 全局状态管理 | 部门树和人员列表是高频复用数据，使用 Pinia（Vue 3）或 Redux（React）做全局缓存，避免重复请求 |
| 拖拽库 | 推荐 `ztree`（jQuery 插件，适合传统项目）或 `react-beautiful-dnd`（React 生态）。若选 Vue 3 技术栈，推荐 `vuedraggable`（基于 SortableJS） |
| 防抖策略 | 实时唯一性校验前端 300ms 防抖，减少无效请求 |

### 3.8 技术栈建议

| 层 | 建议 | 说明 |
|---|---|---|
| 后端框架 | Spring Boot 3.x + MyBatis-Plus | 主流生态，团队熟悉度高 |
| 数据库 | MySQL 8.0 | 树查询可用递归 CTE，物化路径 `path` 字段加速 |
| 缓存 | Redis（可选，v1 可跳过） | 部门树缓存 |
| 前端 | Vue 3 + Element Plus + Pinia | 树组件、拖拽、表单校验、全局状态管理生态成熟 |
| 拖拽库 | vuedraggable（基于 SortableJS） | 轻量，与 Vue 3 深度集成 |
| API 风格 | RESTful | 符合需求文档既定协议 |

## 四、风险与边界条件清单

### 4.1 高风险项
1. **部门树循环引用** — 必须后端校验，禁止将父节点拖到子节点下
2. **审批流级联一致性** — 进行中的审批流不受调动影响；已驳回/已完成的审批不受影响
3. **离职员工数据关联** — 所有关联查询（审批、考勤）必须带上 `employee.status` 过滤
4. **并发唯一性冲突** — 数据库唯一索引是最后防线，不可省略

### 4.2 边界条件
1. 空部门树（初始状态）→ 返回空数组 `[]`
2. 部门下无人员 → 可正常删除
3. 员工调动到同一部门 → 前端应阻止，后端也需校验
4. 已离职员工再次离职 → 返回业务错误
5. 已离职员工调动 → 返回业务错误
6. 根部门不可删除（`parent_id IS NULL`）→ 业务规则

### 4.3 明确不在 v1 范围
- 批量调动 / 批量离职
- 调动审批流
- 部门编码
- 国际化 / 多租户
- 数据导入导出
- 组织架构图可视化（非树形）

## 五、兜底方案（Fallback & Degradation）

> 兜底方案覆盖系统各关键路径的异常场景，确保在依赖故障、性能瓶颈、数据异常时系统仍能提供可接受的服务水平。

### 5.1 数据库层兜底

| 场景 | 兜底策略 | 降级行为 |
|---|---|---|
| 递归 CTE 查询部门树超时（>2s） | 切换为 `path` 字段 LIKE 前缀匹配（`WHERE path LIKE '1-2-%'`） | 无降级，`path` 方案覆盖 100% 场景 |
| `path` 字段与 `parent_id` 不一致 | 定时任务每天凌晨 2:00 全量重建 `path`；API 层发现不一致时用 `parent_id` 递归查询兜底，同时异步修复 `path` | 单次查询耗时增加，但数据正确性不变 |
| 主库连接池耗尽 | 读操作自动切换只读副本（如有）；写操作返回 `503 + 系统繁忙，请稍后重试` | 写操作暂时不可用，读操作正常 |
| 唯一索引写入冲突 | 捕获 `DuplicateKeyException`，返回 `{ "code": 409, "msg": "工号/手机号已存在" }` | 无降级，正常业务错误处理 |

### 5.2 缓存层兜底

| 场景 | 兜底策略 | 降级行为 |
|---|---|---|
| Redis 不可用（连接超时/宕机） | 自动跳过缓存，直接查询数据库；同时异步告警 | 部门树查询耗时增加 50-100ms，功能正常 |
| 缓存数据与 DB 不一致 | 部门树/人员列表缓存 TTL 设为 5 分钟；写操作（增删改）后**主动失效**对应缓存 key | 最多 5 分钟延迟，最终一致性 |
| 缓存雪崩（大量 key 同时过期） | 部门树缓存 key 加随机偏移量（`TTL = 300 + random(0,60)` 秒） | 无影响，预防性措施 |

### 5.3 下游系统依赖兜底

| 场景 | 兜底策略 | 降级行为 |
|---|---|---|
| 审批流系统不可用（调动时级联更新审批节点失败） | 调动操作**先完成员工 dept_id 更新**，审批流节点更新改为异步消息队列；若队列也失败，写入 `pending_sync` 表，定时任务补偿重试 | 调动立即生效，审批流节点最多延迟 5 分钟同步 |
| 权限系统不可用（登录校验） | 本地缓存用户基础权限（角色 + 部门范围），过期时间 30 分钟 | 已有登录 session 不受影响；新登录可能失败 |
| 消息通知不可用 | 静默丢弃，记录日志，不阻塞主流程 | 用户收不到通知，业务操作正常完成 |

### 5.4 并发与限流兜底

| 场景 | 兜底策略 | 降级行为 |
|---|---|---|
| 同一员工并发调动/离职 | 乐观锁（`version` 字段），后者返回 `{ "code": 409, "msg": "数据已被修改，请刷新后重试" }` | 无降级，正常并发冲突处理 |
| 单 IP 高频调用实时校验接口 | 令牌桶限流：每秒 20 次；超过返回 `429 Too Many Requests` | 前端防抖 + 后端限流双层保护 |
| 部门拖拽并发冲突 | 乐观锁，同员工并发策略 | 后者操作失败，前端提示刷新 |

### 5.5 数据一致性兜底

| 场景 | 兜底策略 | 降级行为 |
|---|---|---|
| 调动事务中审批流更新失败 | 员工调动主事务**已提交**，审批流更新失败走 5.3 下游依赖兜底 | 主业务不阻塞，审批流异步补偿 |
| 离职时释放账号许可失败 | 离职状态更新**先提交**，许可释放失败写入 `pending_release` 表，定时任务重试 | 离职立即生效，许可释放延迟（不阻塞） |
| `path` 字段更新失败（拖拽时） | 不阻塞拖拽事务，`parent_id` 更新成功后异步重建 `path` | 拖拽立即生效，`path` 不一致时走 5.1 兜底 |

### 5.6 部署与回滚

| 场景 | 策略 |
|---|---|
| 新版本上线后核心接口错误率 > 1% | 立即回滚到上一个稳定版本；数据库迁移脚本必须有对应回滚脚本 |
| 数据库迁移失败 | 所有 DDL 变更必须包含 `IF NOT EXISTS`；破坏性变更（删除列/表）需延迟一个版本执行 |
| 灰度发布 | 先部署 1 台实例观察 10 分钟，无异常再全量 |

### 5.7 监控与告警阈值

| 指标 | 告警阈值 | 处理动作 |
|---|---|---|
| 部门树接口 P99 响应时间 | > 500ms | 检查缓存命中率、数据库慢查询 |
| 实时校验接口错误率 | > 5% | 检查数据库连接池、限流触发次数 |
| 异步补偿任务积压 | > 100 条 | 排查下游系统可用性 |
| `path` 不一致记录数 | > 0 | 立即触发全量重建 |
