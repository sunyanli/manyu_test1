## 二、Blocker 清单（阻塞项）

### Blocker #1: 缺口 #2 诊断信息分类与缺口 #9 超时策略存在语义重叠

**严重级别**: 🔴 Blocker

**位置**: 缺口 #2 (第 96-108 行) vs 缺口 #9 (第 193-203 行)

**问题描述**:
- 缺口 #2 定义了失败原因分类 `command_not_found / config_error / runtime_error / timeout`
- 缺口 #9 独立定义了超时策略（300s 默认超时、`test_timeout` 配置项）
- 两处均涉及 `timeout` 场景，但未说明：
  - 缺口 #2 的 `timeout` 分类与缺口 #9 的超时策略是否属于同一错误路径？
  - 超时发生时，诊断信息应同时包含缺口 #2 的四个字段 _和_ 缺口 #9 的标注文案，还是二者选一？
  - `test_timeout` 配置项是否应联动 `timeout` 分类码？

**建议**: 合并缺口 #2 和 #9 为一组需求，统一超时/诊断信息规范，避免设计阶段产生两个独立但互引的错误处理路径。

---

### Blocker #2: 覆盖率 IR 的定义与 NFR5 插件式架构的解析器职责边界未定义

**严重级别**: 🔴 Blocker

**位置**: 缺口 #11 (第 219-238 行)

**问题描述**:
- 缺口 #11 定义了覆盖率标准化 IR（JSON schema），但未说明：
  - 该 IR 是解析器（Parser）的输出还是报告渲染器（Renderer）的输入？
  - 若某覆盖率工具仅输出 `lines` 维度（如部分简易工具），IR 中缺失字段（`branches`、`functions`）应如何处理？
  - 解析器是否强制要求产出完整 IR，还是允许部分字段为 `null`？
- 这直接影响 NFR5 插件式架构的接口契约设计。

**建议**: 在 IR 定义中明确：
  - 每个维度字段为可选（缺省 = `null`），渲染器对 `null` 字段标注"未获取"；
  - 解析器接口契约：`parse(coveragePath) → CoverageIR`，IR 由渲染器消费；
  - 补充 `files` 维度（文件级覆盖率列表），以支持"低于阈值的文件清单"。

## 三、主要发现（Major Findings）

### M1: 缺口 #7 截断策略与缺口 #4 目录创建存在隐式依赖

**严重级别**: 🟡 Major

**描述**: 缺口 #7 建议"截断时在附录保留原始结果文件路径"，但原始结果文件路径依赖于：
- 执行模式：结果文件由 Skill 自动生成，路径已知；
- 解析模式：结果文件路径由用户指定 (`result_file` 配置项)。

若用户走解析模式且 `result_file` 为相对路径，截断提示中的路径可能无法被后续读者定位。建议附录中统一使用绝对路径。

---

### M2: 边界条件 E8 与 FR1.1 多框架检测逻辑存在潜在冲突

**严重级别**: 🟡 Major

**描述**: 
- E8 规定"多个测试框架同时产生结果时，优先使用框架原生格式（JSON），JUnit XML 作为兜底不冲突"
- 但 FR1.1 的检测优先级（缺口 #1 建议方案）仅处理了配置文件层面的推断，未覆盖"执行后同时产出 Jest JSON + JUnit XML"的场景
- 当用户同时配置了 Jest 的 JSON reporter 和 JUnit reporter 时，E8 的优先级规则是否仍然适用？

**建议**: 在 FR1.1 中补充"结果收集阶段"的优先级：框架原生 JSON > JUnit XML（同目录），与 E8 保持一致。

---

### M3: 缺口 #5 fail_threshold 默认值 0 的语义可能导致误用

**严重级别**: 🟡 Major

**描述**: 缺口 #5 建议 `fail_threshold` 默认值为 `0`（即不启用），比较规则为"通过率 < fail_threshold 时触发"。但 `0` 的语义存在歧义：
- 若通过率 = 0%（全部失败），`0 < 0` 为 false，不触发不达标；
- 用户可能期望"通过率 = 0% 时显然不达标"，但默认行为不会标记。

**建议**: 默认值改为 `-1`（表示不启用），或将比较规则修正为 `通过率 <= fail_threshold`（当 fail_threshold=0 时，0% 通过率也会触发）。

---

### M4: 缺口 #8 数据一致性验证标准缺少"跳过数"和"耗时"的跨框架差异处理

**严重级别**: 🟡 Major

**描述**: 缺口 #8 建议"用例总数、通过/失败/跳过数精确匹配"，但不同框架对"跳过"的定义不同：
- Jest: `pending` + `skipped` 均计入跳过；
- Vitest: 仅 `skipped` 计入；
- pytest: `skipped` 含 `skip` 和 `xfail`。

若不做语义归一化，精确匹配的要求可能导致假阳性验证失败。

**建议**: 在 M1 设计阶段定义各框架结果字段到报告模型的映射表，明确"跳过"的归一化规则。

## 五、安全检查（Security Review）

参照 NFR3 与缺口 #6 的安全设计：

| 检查项 | 状态 | 说明 |
|--------|------|------|
| 凭据过滤策略 | ⚠️ 需增强 | 缺口 #6 的过滤正则过于宽泛，见 Minor m2 |
| 环境变量泄露 | ✅ 已覆盖 | 缺口 #6 明确过滤目标含 `AWS_SECRET_*`、`API_KEY` 等 |
| 堆栈路径过滤 | ⚠️ 未定义 | 仅过滤"凭据内容"，未提及是否过滤用户主目录路径（如 `/home/username/`） |
| 报告文件权限 | ❌ 缺失 | 未定义生成的报告文件权限（如 0644），可能在多用户环境中泄露 |
| 注入风险 | ❌ 缺失 | 若测试用例名包含 Markdown 特殊字符（如 `#`、`|`），报告渲染可能产生格式破坏 |

**安全建议**:
1. 增加报告文件权限规范：默认 `0644`（owner 可读写，其他只读）；
2. 增加 Markdown 转义规则：用例名、错误信息中的 `|`、`#`、`<`、`>` 等字符须转义；
3. 增加用户主目录路径脱敏规则（替换为 `$HOME`）。
